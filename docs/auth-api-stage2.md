## Что подключено

| Действие | Запрос | Чтение ответа |
| --- | --- | --- |
| Dropdown | GET /public/auth/users | data.usernames: массив строк |
| Вход | POST /public/auth/login | data.accessToken, data.refreshToken |
| Обновление | POST /public/auth/refresh, refreshToken в JSON | Новая пара внутри data |
| Текущий сотрудник | GET /protected/me с Bearer | data.employeeId, username, role |
| Смена своего пароля | PUT /protected/me/change-password с Bearer | Стандартная оболочка, data: null |
| Выход | POST /protected/me/logout с Bearer, без тела | Стандартная оболочка, data: null |

Существующие слои сохранены: HttpTransport → AuthApiDataSource → AuthRepository
→ AuthService → AuthProvider → экран входа. Публичная регистрация и debug bypass
удалены. Пустое поле пароля передаётся как пустая строка.

AuthService реализует Listenable и подключается через ListenableProvider<AuthService>.
AuthProvider подключается через ChangeNotifierProvider. Обычный Provider для
AuthService не используется: он не подписывается на уведомления сервиса.

В рабочем экране меню текущего сотрудника содержит смену пароля и выход.
Имя и роль приходят из /me. Проверка доступа остаётся на сервере.

## Сессия

При запуске рабочий экран ждёт восстановления. Сохранённый refresh отправляется
на сервер; затем загружается /me. При временном сбое показываются сообщение,
«Повторить» и возможность локального выхода. Refresh не удаляется из хранилища
из-за таймаута, сети, 5xx или некорректного ответа.

Пара JWT сохраняется одной записью flutter_secure_storage. Access и пользователь
публикуются только после успешного /me и сохранения. Старые отдельные ключи
читаются для совместимости; выход удаляет и новые, и старые ключи.

AuthService.authenticatedRequest используется общим ApiClient и сменой пароля:
401 запускает общий refresh, каждый запрос повторяется не более одного раза.
403 защищённого запроса не запускает refresh. Окончательный отказ refresh или
повторный 401 завершает локальную сессию и уведомляет AuthProvider.

Выход не ждёт ответа сервера. Версия сессии и последовательная запись в
хранилище не позволяют запоздалому refresh восстановить завершённый вход или
перезаписать токены следующего сотрудника. Ответы защищённых запросов от
предыдущей сессии отбрасываются.

Рабочие Provider и навигация создаются заново для новой сессии. Завершившиеся
после их удаления запросы не уведомляют уже уничтоженные Provider.

## Запуск пользователем

API_BASE_URL — адрес сервера без дополнительного /public или /protected.
По умолчанию используется http://localhost:8000. Сервер должен быть запущен отдельно.

```powershell
flutter run -d windows --dart-define=API_BASE_URL=http://localhost:8000
```

Для сервера на другом компьютере укажите его адрес локальной сети в API_BASE_URL
как начальное значение или измените URL через ⋮ «Приложение» → «Настройки подключения…».
Сохранённый URL имеет приоритет; см. [настройки сервера](server-settings.md).
HttpTransport ограничивает весь запрос, включая чтение ответа, 15 секундами.

```powershell
flutter test test/auth
```

Сценарии для повторной ручной проверки с реальным API:

Рабочая авторизация подтверждена пользователем. Список ниже сохраняется для
регрессионной проверки и не означает отдельного отчёта о каждом сценарии.

1. Загрузить список, выбрать сотрудника, войти с обычным и установленным пустым паролем.
2. Проверить отказ при неверном пароле; имя сотрудника на рабочем экране.
3. Перезапустить приложение и проверить восстановление без пароля.
4. Проверить refresh после истечения access token.
5. Остановить сервер, перезапустить приложение: сохранённый вход остаётся,
   «Повторить» восстанавливает его после запуска сервера.
6. Изменить свой пароль на пустой и обратно; текущий вход сохраняется.
7. Выйти при недоступном сервере; следующий запуск открывает вход.
8. Войти другим сотрудником; прежние страницы, фильтры и незавершённые формы сброшены.
