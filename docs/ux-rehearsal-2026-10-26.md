## UX-01. Сохранение правок маршрута закрывает документ

Статус: реализован третий этап, автоматические проверки успешны;
ожидается ручная проверка перед коммитами. См. [ux-stage3-review.md](ux-stage3-review.md).

Шаги: открыть сохранённый маршрут → нажать «Редактировать» → изменить
количество воды с 2 на 3 → нажать «Сохранить».

Фактически: данные правильно сохраняются, но приложение сразу возвращает
пользователя на дашборд. Переход оказался непредсказуемым.

Ожидается: после успешного сохранения изменений показать тот же маршрут
в режиме просмотра с актуальными сохранёнными данными. Выход на дашборд —
отдельное действие пользователя.

Влияние: потеря контекста и лишнее повторное открытие для проверки результата.
Ошибки сохранения данных в этом сценарии пользователь не обнаружил.

Подтверждение по коду: DeliveryDocumentEditor._save() после widget.save()
вызывает _close(afterSave: true), который закрывает документ и выполняет
Navigator.pop(). Общий редактор используется также для самовывоза;
поведение самовывоза в ручном сценарии пока не проверено.

План после тестирования:

1. Для редактирования существующего маршрута заменить закрытие после
   успешного сохранения переходом в режим просмотра этого документа.
2. Проверить markDocumentSaved(), актуализацию данных из ответа сервера,
   сброс признака несохранённых правок и освобождение блокировки редактирования.
   Сохранить уведомление дашборда об изменении документа.
3. При ошибке сохранения оставлять редактор с введёнными данными и ошибкой.
   После успеха обеспечить возможность повторно войти в редактирование.
4. Отдельно определить поведение после создания нового документа и при
   сохранении самовывоза; текущее замечание подтверждено для правок маршрута.
5. Проверить цепочку: открыть → редактировать → сохранить → увидеть новые
   данные в просмотре → повторно редактировать → выйти → открыть с дашборда.
   Проверить отсутствие зависшей блокировки и регрессий общего редактора.

## UX-02. Стрелка назад из редактирования закрывает документ

Статус: реализован третий этап для стрелки AppBar и системного возврата,
автоматические проверки успешны; ожидается ручная проверка перед коммитами.
См. [ux-stage3-review.md](ux-stage3-review.md).

Проверенный успешный сценарий: изменить количество с 3 на 4 без сохранения →
нажать «Отмена» → вернуться в просмотр. В просмотре осталось количество 3.
Пользователь оценил кнопку и поведение как интуитивно понятные.

Замечание: при использовании стрелки возврата в AppBar из режима
редактирования приложение возвращает на дашборд. Пользователь ожидает
возврата к просмотру того же документа.

Влияние: разные способы выхода из редактирования ведут в разные места,
нарушая ожидаемую последовательность «просмотр → редактирование → просмотр».
Наличие предупреждения при выходе стрелкой с несохранёнными изменениями
и сохранность данных именно в этой ветке пока отдельно не подтверждены.

План после тестирования:

1. В режиме редактирования существующего документа направлять стрелку
   AppBar через отмену редактирования и возврат к просмотру того же документа.
2. Использовать общий механизм отмены с кнопкой «Отмена»: восстановление
   сохранённых данных, сброс несохранённых изменений и освобождение блокировки.
   Проверить существующее предупреждение о несохранённых изменениях и
   согласованность его применения для обоих способов отмены.
3. В режиме просмотра оставить стрелку способом выхода на дашборд.
   Отдельно проверить навигацию при создании нового документа и самовывозе.
4. Проверить оба способа отмены с изменениями и без них, сохранность
   количества 3 и суммы 1050, повторное редактирование и выход из просмотра.

## UX-04. Внутренние разделители задания обрываются в маршрутном листе

Статус: подтверждено пользователем и скриншотом PDF, исправление после тестирования.

Фактически: вертикальные границы столбцов задания (#, продукция, количество,
цена, сумма) заканчиваются после строки товара, выше общей нижней границы
блока клиента. Получаются незамкнутые линии и впечатление сломанной таблицы.

Ожидается визуально завершённая сетка. Пользователь допускает два решения:
продлить вертикальные границы до низа общего блока либо замкнуть таблицу
товаров под последним товаром горизонтальной границей.
Конкретный вариант выбрать при исправлении по результату визуальной проверки.

План: согласовать высоту вложенной таблицы задания с блоком клиента либо
добавить явную нижнюю границу последней строки. Сохранить читаемость и
выравнивание итогов. Проверить рендер PDF с одним и несколькими товарами,
длинными данными клиента и переносом на следующую страницу.

## UX-05. Подтверждение отмены не объясняет последствия

Статус: зафиксировано пользователем, исправление после тестирования.

Фактически: текст «Документ будет отменён. Несохранённые изменения формы
не сохранятся.» непонятен пользователю. Кнопки и сама операция работают нормально.
Требование: убрать фразу о несохранённых изменениях из подтверждения отмены
документа и объяснить бизнес-последствия.

Контракты backend проверены:
- delivery_days.md, строки 51 и 61: отменённый документ исключается из
  показателей дня; карточка даты с отменёнными документами остаётся с нулями.
- commissions.md, раздел «Общие правила периода и денег»: отменённые документы
  исключаются из расчётов вознаграждений обоих типов получателей.
- delivery_document.md, раздел «Отмена и восстановление»: данные сохраняются,
  документ доступен через фильтр отменённых, редактирование запрещено до
  восстановления; восстановленный документ снова учитывается в отчётах.
- Отмена не откатывает ранее записанный пробег машины; в общем диалоге
  не обещать полного отката всех последствий документа.

Предлагаемый текст:
«Документ не будет учитываться в показателях дня доставки и расчётах
вознаграждений торговых представителей и менеджеров офиса.
Данные сохранятся — документ можно будет просмотреть и восстановить.»

План: заменить текст в общем DeliveryDocumentEditor, проверить доставку
и самовывоз, длинный текст и соответствие сообщения восстановлению.
Использовать термин заказчика «менеджеры офиса» вместо технического
обозначения «сотрудники офиса» в этой пользовательской формулировке.

Дополнение после ручного восстановления: текущий текст восстановления
слишком общий и не объясняет последствия. Пользователь просит сделать
его конкретнее. Предлагаемый текст:
«Документ снова будет учитываться в показателях дня доставки и расчётах
вознаграждений торговых представителей и менеджеров офиса.
Будут восстановлены сохранённые данные документа и доступ к редактированию.»
При реализации не обещать пересчёт по текущим ставкам: по контракту
возвращаются сохранённые исторические начисления.

## UX-08. Ошибка количества сжимает поле, текст слишком краткий

Статус: подтверждено пользователем и скриншотом, исправление после тестирования.

При ручном вводе 0 показывается «Больше 0», поле визуально сжимается снизу.
В TaskItemRow блок количества ограничен высотой 48; появление errorText

это заменяет первоначальное предложение текста «Минимум 1».

Актуальный план: убрать видимый текст ошибки и место под него только для
поля количества. Оставить явный визуальный сигнал недопустимого ввода
(ошибочную рамку поля), сохранить высоту ввода и выравнивание кнопок −/+,
цены и суммы. Не добавлять отдельные Text/SnackBar. Сохранить проверку ввода
и невозможность передать недопустимое количество при сохранении; учесть
оба пути проверки (validator и onChanged), чтобы текст не появлялся снова
при нажатии «Сохранить». Проверить узкую/широкую раскладку и масштаб текста,
при необходимости оставить невизуальное пояснение для доступности.
Повторно использовать существующие TaskItemRow и AppIconButton.
Это прямое пожелание пользователя для этого поля; общие правила ошибок
остальных полей не меняются.

Работающие ограничения сохранять: 0 не передаётся в количество заказа и
не сохраняется; при потере фокуса поле возвращает допустимое значение;
«−» отключена при количестве 1. Наблюдение пользователя: поле вернулось к 1,
сумма при недопустимом вводе не изменилась. Механизм по коду восстанавливает
текущее допустимое widget.item.quantity, а не безусловно устанавливает 1.

## UX-09. Разделить выбор клиента и добавление в документ

Статус: требование пользователя, реализация после тестирования.

Ожидаемое взаимодействие в списке клиентов конструктора маршрута/самовывоза:
- Зелёная кнопка внутри элемента добавляет клиента в документ.
- Нажатие на сам элемент только выбирает клиента для последующего
  редактирования, не добавляет его в документ и не открывает редактор сразу.
- Выбранный элемент заметно выделяется фоном; изменения одного цвета текста
  недостаточно. Выделение сохраняет читаемость и отличается от наведения.

План: в ClientSelectionPanel разделить обработчик выбора и добавления,
превратить зелёный значок в отдельную доступную кнопку добавления с подсказкой,
сохранить доступ к редактированию выбранного клиента. Использовать фон
выбранного элемента из темы, проверить светлую/тёмную тему и наведение.
Повторно использовать ClientSelectionPanel и существующие AppIconButton/
AppDropdown, без создания дублирующих компонентов.
Проверить защиту от повторного добавления, уже добавленных и деактивированных
клиентов; простое выделение не должно активировать или добавлять клиента.
Учесть общий обработчик выбора в dropdown и автоматическое добавление после
сохранения клиента: не оставлять обходные пути, из-за которых редактирование
существующего клиента неожиданно создаёт точку. Поведение создания нового
клиента по месту рассмотреть отдельно, не менять ранее одобренный сценарий

## UX-12. Потеря связи показывает несохранённые правки как просмотр документа

Статус: первый этап реализован 27 октября в текущих ветках обоих проектов,
без коммитов. Автоматические проверки и основные ручные сценарии успешны:
восстановление ввода, чужая блокировка, изменённая версия и новая форма.
Скачок диалога при появлении спиннера исправлен и подтверждён пользователем.
Этап готов к просмотру изменений и коммитам пользователя.
Результат и сценарии: [ux-stage1-review.md](ux-stage1-review.md).

Сценарий: последний самовывоз Бориса (700 ₽, 2 бутылки) открыт для
редактирования, введено 3 бутылки, локальный API репетиции остановлен.
Пользователь сообщает: экран перешёл в просмотр с количеством 3, появились
сообщения о потере связи/блокировки; повторное редактирование выдаёт понятную
ошибку запроса. В базе напрямую проверен этот документ: сохранено 2 × 350 ₽,
то есть 700 ₽. Отображаемые 3 бутылки не являются сохранёнными данными.

Причина по коду: OrderPointsProvider._renewDocumentLock() при любой ошибке
продления блокировки отключает isEditing, останавливает таймер и показывает
«Блокировка потеряна», но оставляет изменённые points на экране. Отсутствие
связи само по себе не доказывает, что серверная блокировка потеряна.

Актуальное целевое поведение и план (уточнено пользователем):
1. Разделить сетевую недоступность и подтверждённую сервером утрату права
   редактирования. Отключать сохранение при невозможности подтвердить право,
   но не представлять локальные правки как сохранённый режим просмотра.
2. В создании и редактировании перекрывать экран модальным диалогом
   «Нет связи с сервером» с кнопкой «Повторить подключение». Пока связь
   не проверена, ввод и сохранение недоступны; диалог нельзя закрыть кликом
   снаружи или Escape и обойти блокировку ввода. Состояние формы сохранять
   в памяти, не переводить её в обычный просмотр только из-за сетевого сбоя.
3. Текст должен объяснять, что введённые данные остаются в открытой форме,
   а продолжение требует восстановления связи. При неопределённом исходе
   сохранения не утверждать, что сервер точно не сохранил запрос.
4. Как только связь доступна, без дополнительного нажатия «Редактировать»
   максимально быстро продлить прежнюю блокировку или, если она истекла,
   атомарно получить новую от имени того же сотрудника. Проверка выполняется
   при «Повторить подключение»; при фоновых повторах исключить параллельные
   запросы и частый бесконечный опрос. Действующую чужую блокировку не вытеснять.
   Если документ не изменился и право получено, закрыть диалог и продолжить
   редактирование с сохранённым локальным вводом. Для новой формы без ID
   проверить доступность API, блокировка документа не нужна.
5. Если сервер подтверждает чужую блокировку, пользователь требует
   принудительно отменить текущее редактирование, отбросить локальные правки
   и вернуть режим просмотра актуальных сохранённых данных. Показать явное
   сообщение: «Редактирование прекращено: документ редактирует <имя>.
   Несохранённые изменения отменены». Если загрузка данных не удалась,
   оставаться в состоянии ошибки/загрузки, не показывать локальные 3 как
   сохранённые данные. Это заменяет прежний план выбора слияния при конфликте.
6. Одного успешного повторного получения свободной блокировки недостаточно:
   другой сотрудник мог успеть изменить документ и освободить её. Сверять
   актуальное серверное состояние с исходным состоянием редактора, включая
   исход неоднозначного сохранения. При реальном чужом изменении также
   прекратить устаревшее редактирование с объяснением и загрузить просмотр.
   Проверить, потребуется ли версия документа/API для надёжной проверки.

   Предлагаемое решение для согласования: целочисленная версия документа
   revision (начальная 1), возвращаемая в GET/создании/изменении документа.
   Увеличивать атомарно при успешном изменении содержимого, отмене и
   восстановлении. Изменения дочерних точек/строк также меняют версию корневого
   документа; получение/продление блокировки и просмотр версию не меняют.
   При открытии редактора запоминать исходную версию. Сохранение передаёт
   expectedRevision; backend в той же транзакции проверяет действующую
   блокировку и совпадение версии, записывает данные и увеличивает revision.
   При несовпадении отклоняет запись как конфликт версии без изменения данных.
   Использовать различимый код ошибки конфликта, так как HTTP 409 уже имеет
   другие значения. После повторного получения блокировки сравнивать версии:
   чужое изменение → прекратить редактирование и загрузить актуальный просмотр.
   Если за время ошибки сохранение могло успешно выполниться, сначала сверить
   результат/исход операции, не объявлять любое увеличение версии чужим
   изменением и не отправлять повторный запрос автоматически.
   Для неоднозначного результата рассмотреть ID операции/идемпотентность
   отдельно; версия сама по себе не идентифицирует автора последней записи.
   updatedAt можно добавить для истории/отображения, но не использовать вместо
   revision для защиты от конкурентной записи. Это изменение схемы/API/
   контрактов и обоих Flutter-конструкторов, реализация после тестирования.
7. Не отправлять сохранение автоматически: повторное сохранение — явное
   действие пользователя. Если запрос мог дойти до сервера, сначала сверить
   состояние документа, не утверждать без проверки, что он не сохранился.
8. Проверить доставку и самовывоз, краткий/долгий сбой, истечение блокировки,
   изменение другим сотрудником, повторное сохранение и отказ от правок.

Для продолжения ручного сценария API вновь запущен на порту 8001.
Код приложения не менялся. После восстановления API пользователь повторно
нажал «Редактировать»: количество 3 осталось в редактировании. Локальный
ввод в данном сценарии сохранился, но режим просмотра до этого показывал
несохранённые данные, что остаётся дефектом.

## Диагностика окружения: адреса/Geoapify после hot reload

27 октября тест оптимизации остановлен: адреса ещё не подтверждены, попытка
поиска адреса во Flutter показывает «Сессия не восстановлена».
Ключ Geoapify присутствует и совпадает в .env и .env.rehearsal (значения
не выводились). Прямой запрос к Geoapify из разрешённого запуска успешен:
HTTP 200, 5 кандидатов для тестового адреса. Тот же функциональный endpoint
API репетиции возвращает 503 GeoUnavailable; API запущен в ограниченном
окружении, требуется перезапуск с внешним сетевым доступом.

Сообщение «Сессия не восстановлена» генерирует локально AuthServiceImpl до
запроса. Вероятная причина по main.dart — hot reload во время исправления
UX-18: _configuredApplication создаёт новые authService/apiClient, .value-
провайдеры обновляются, а create-провайдеры AuthProvider/AuthServiceImpl
сохраняют прежние экземпляры. LocationRepository может получить новую
неавторизованную сессию, хотя интерфейс остаётся авторизованным со старой.
Для продолжения — полный перезапуск Flutter после закрытия несохранённых
форм. Изменение композиции зависимостей пока не выполнять; сначала проверить,
что чистый запуск устраняет ошибку. Это диагностика разработки, ещё не
подтверждённый дефект обычной release-сборки.

После закрытия пользователем несохранённых форм API перезапущен с внешним
доступом. Повторный запрос /protected/clients/geocode успешен: HTTP 200,
1 кандидат. Прежнее окно Flutter закрыто штатно, выполнен полный запуск
вместо hot reload. Следующая проверка пользователя — поиск и подтверждение
адресов обоих клиентов через интерфейс.
