# Этап 1: потеря связи и безопасное восстановление документа

Ветка обоих проектов: `codex/ux-rehearsal-fixes`. Коммиты делает пользователь.

## Изменения

- В создании и редактировании потеря связи перекрывает форму диалогом с
  кнопкой «Повторить подключение». Ввод остаётся в памяти открытой формы;
  Escape и клик вне диалога не открывают доступ к данным. Есть автоматическая
  проверка каждые 5 секунд, параллельные повторы исключены.
- При восстановлении существующего документа сразу запрашивается право
  редактирования и проверяется версия. Если версия прежняя, работа продолжается
  с локальными правками. При чужой блокировке, отмене или изменении документа
  правки отменяются, загружается актуальный просмотр и показывается причина.
- Backend атомарно проверяет `expectedRevision` вместе с правом редактирования.
  Устаревшая версия отклоняется с отдельным кодом конфликта, без записи данных.
- Идентификаторы сохранения позволяют распознать потерянный ответ. Для создания
  повтор с тем же ключом и телом возвращает тот же документ; повтор с другим
  телом запрещён. Автоматического сохранения после восстановления нет.
- Доставка и самовывоз используют общий механизм. Переиспользованы
  `DeliveryDocumentEditor`, `OrderPointsProvider`, `AppPrimaryButton` и штатный
  `AlertDialog`. Новый `DocumentConnectionDialog` содержит только представление
  состояния связи для обоих редакторов.

## Что проверить вручную вместе

Первая ручная проверка: пользователь подтвердил, что диалог при остановленном
API перекрывает ввод и работает ожидаемо. Замечен скачок размера при появлении
спиннера. Исправлено: постоянный слот 32 × 40 с индикатором 18 × 18;
два регрессионных widget-теста (ширина 800 и 420) подтвердили неизменность
размера диалога и положения кнопки. Для сохранения текущих несохранённых
3 бутылок исправление пока не загружалось в открытый процесс: сначала
завершить восстановление/отмену, затем перезапустить приложение.

После запуска API пользователь подтвердил автоматическое восстановление
связи: диалог закрылся, режим редактирования полностью доступен, введённые
3 бутылки остались. Автосохранение не выполнялось. Следующий шаг — отмена
правок с возвратом сохранённых 2 бутылок, затем полный запуск с исправленным
размещением спиннера.

Пользователь подтвердил: после «Отмена» вернулись сохранённые 2 бутылки
и 700 ₽. Короткий обрыв → автоматическое восстановление → отмена правок
проверены вручную полностью. После этого приложение перезапущено для
применения исправления спиннера.

Ручная проверка чужой блокировки выполнена: при выключенном API право
передано rehearsal_admin через штатные use cases (без изменения содержимого
документа), затем API запущен. Пользователь подтвердил закрытие диалога,
возврат в просмотр с 2 бутылками и 700 ₽, понятное объяснение с именем
rehearsal_admin. Спиннер больше не меняет размер диалога. Тестовая чужая
блокировка после проверки освобождена штатно.

Проверка изменённой версии при свободной блокировке выполнена вручную.
Во время остановки API через штатные use cases другой сотрудник сохранил
4 бутылки (1400 ₽), версия выросла 1 → 2, запись прочитана обратно из базы,
блокировка освобождена. После запуска API пользователь подтвердил просмотр
с 4 бутылками и 1400 ₽ и сообщение об изменении документа/отмене правок.
Локальные 3 не перезаписали серверные 4. Следующий шаг — вернуть 2 бутылки
обычным сохранением через интерфейс, затем проверить создание при обрыве.

1. Короткий обрыв: изменить 2 бутылки на 3, не сохранять; остановить API.
   Диалог блокирует форму. После запуска API диалог исчезает, остаётся 3,
   режим редактирования сохранён. Отмена возвращает сохранённые 2.
2. Создание: заполнить новую форму и повторить обрыв. После восстановления
   данные остаются, документ не создаётся сам. Сохранить ровно один раз.
3. Чужая блокировка: при обрыве дать прежней блокировке истечь, занять документ
   другим сотрудником. При восстановлении первый редактор отменяет правки,
   показывает актуальный просмотр и имя сотрудника.
4. Изменённый документ со свободной блокировкой: второй сотрудник сохраняет
   изменение и выходит. Первый редактор обнаруживает новую версию и открывает
   актуальный просмотр без перезаписи.
5. Потерянный ответ записи: сервер успел сохранить, ответ не дошёл. После
   восстановления приложение показывает подтверждённый результат без второй
   записи/дублирующего документа. Этот случай проверен автоматически;
   для ручной имитации нужен управляемый разрыв ответа.

Сначала пройти пункт 1 в самовывозе, затем в доставке. API останавливает и
восстанавливает агент по сигналу пользователя, не меняя базу.

## Границы этапа

Остальные UX-замечания пока не реализованы: навигация после обычного успешного
сохранения, оформление сообщения о занятом документе, комиссии, PDF и т. д.
Backend и Flutter нужно выпускать согласованно: старый клиент без версии
получит 422 при PATCH. После hot reload в этом проекте ранее наблюдалось
рассогласование авторизации; стенд перезапущен полностью, это отдельная задача.
