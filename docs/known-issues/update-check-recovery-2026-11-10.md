# Windows updater: ручная проверка не восстанавливается без перезапуска

**Дата наблюдения:** 10.11.2026.  
**Статус:** отложено; не исправлять в рамках выпуска v1.3.0.  
**Область:** Flutter Windows, обновление с `1.2.0+42` на `1.3.0`.  
**Приоритет для будущей оценки:** высокий для UX обновления при обязательном
повышении минимальной версии клиента; техническая причина пока не подтверждена.
**Рабочая ветка для записи:** `codex/update-check-recovery-backlog`;
никаких изменений `master` и release artifacts.

## Наблюдение владельца

Во время последовательного выпуска:

1. Backend уже начал требовать клиент **не ниже `1.3.0`**, а публичный
   Flutter `v1.3.0` ещё не был опубликован.
2. Открытое приложение `1.2.0+42` показало экран «Требуется обновление»
   и текст «Требуется приложение: 1.3.0 или новее».
3. Через «Обновить приложение» открылся диалог
   **«Версия 1.2.0+42 — Обновления недоступны в этой сборке.»**
   (скриншот передан владельцем в разговоре; в Git не добавляется).
4. После публикации нового Flutter Release приложение **без перезапуска**
   не обнаруживало его при ручном обновлении/проверке из меню.
   Повторная проверка совместимости с backend также не помогла.
   Переключение API на другой адрес и обратно не помогло.
5. **Полное закрытие и повторный запуск приложения помогли:** на меню
   появилась отметка о новой версии, приложение увидело опубликованный
   релиз. Успешная установка обновления в данном наблюдении отдельно
   не подтверждалась.

**Влияние:** старый клиент уже заблокирован политикой совместимости backend,
а человек не может получить новое обновление из запущенного приложения
до перезапуска. При следующем выпуске это способно выглядеть как отсутствие
нового релиза или сломанный механизм обновления.

## Подтверждённое по исходникам `v1.2.0` и `master`

- `lib/features/app_updates/ui/update_provider.dart`:
  `start()` получает установленную версию → `initialize()` →
  `ready = true` → `check()` → ставит таймер **каждые 4 часа**.
  При исключении в `start()` выставляет текст
  **«Обновления недоступны в этой сборке.»**; `ready` может
  остаться `false`, а таймер не запускается.
- `check()` немедленно завершает работу при `!ready`; кнопка
  «Обновить приложение» и ручная проверка из меню вызывают именно
  `UpdateButton.open() → updates.check()`. Такой путь **не повторяет
  `initialize()`**, когда стартовая инициализация не состоялась.
- `lib/features/app_updates/update_service.dart`:
  метаданные `update.json` загружаются отдельно от native WinSparkle.
  **HTTP 404** трактуется как отсутствие первого релиза. Если
  `ready == true`, ручная проверка должна снова обратиться к GitHub;
  одна лишь публикация позднее не объясняет ошибку инициализации.
- `windows/runner/update_bridge.cpp`:
  повторный вызов native `initialize` при `initialized_ == true`
  возвращает ошибку `Invalid or repeated initialization`.
  `lib/main.dart` создаёт `UpdateProvider` в конфигурируемом
  дереве приложения, которое может пересоздаваться при смене сервера.
  **Возможна проблема жизненного цикла при смене API**, но это
  требует отдельной проверки.
- `docs/windows-updates.md` описывает проверку при запуске и раз
  в четыре часа. Эта периодичность **не гарантирует восстановления**
  после провала `start()`.

**Предварительная гипотеза:** одноразовый сбой `UpdateProvider.start()`
(получение версии, native initialization или иной exception) оставил
updater неготовым. Из-за `ready == false` ручной `check()`
не делает запрос, а таймер не был установлен. Повторное создание
провайдера при смене API могло дополнительно привести к повторному
native `initialize`. **Нет журналов/событий native и HTTP, поэтому
точная первопричина, время и конкретный exception не установлены.**
Не приравнивать этот инцидент автоматически к ранее отмеченному
N6-01 (неточные сообщения самого WinSparkle) или к исправленному
S6-01 (Dart-диагностика HTTP).

## Что исследовать в отдельной задаче

1. Воспроизвести сценарий `v1.2.0` с открытым приложением:
   первоначально релиз/metadata недоступны → публикуются или
   становятся доступными → пользователь вручную проверяет без restart.
   Отдельно искусственно провоцировать exception в
   `installedVersion` / `initialize` / `latest`.
2. Проверить `ready`, `error`, события platform channel,
   число вызовов `initialize`, HTTP-запросы к `update.json`
   и `appcast.xml`, создание/отмену 4-часового таймера.
   Не записывать закрытые ключи, токены и данные заказчика.
3. Проверить смену адреса backend с пересозданием
   `ServerApplicationScope` и реакцию native bridge на повторную
   инициализацию. Отдельно протестировать экран обязательного обновления.
4. Продумать **явное восстановление updater по ручному нажатию**:
   безопасный повтор инициализации либо независимая проверка метаданных,
   понятная диагностика, отсутствие ложного «обновления не настроены»,
   защита от параллельных проверок и двойных native init.
5. Нужны регрессионные тесты с восстановлением после init failure,
   публикацией релиза уже после запуска приложения, server switch,
   cancellation/error/retry и реальным Windows smoke.
   Не ослаблять Ed25519, HTTPS feed allowlist, блокировку редактора
   или ограничения обязательного обновления.

## Временный обходной путь

**Полностью закрыть и вновь запустить приложение.** Это сработало
в описанном наблюдении, но не является исправлением.
После дальнейшей диагностики определить, можно ли сделать ручную
кнопку действительно восстанавливающей проверку без перезапуска.

**Не входит в текущую запись:** изменения кода, тестов, CI, тегов,
публичного релиза, backend, рабочих ПК или production.
