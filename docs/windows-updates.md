# Установщик и обновление Windows

Приложение устанавливается для текущего пользователя в
`%LOCALAPPDATA%\Programs\MountainFairytale`. Администратор и доступ к backend
для обновления не нужны. Источник — публичные GitHub Releases этого репозитория.
Первый Setup.exe устанавливается вручную, дальнейшие обновления запускаются
кнопкой со значком обновления в верхней панели.

## Однократная настройка владельцем

Из корня Flutter-проекта, в обычном PowerShell:

```powershell
.\scripts\windows\new-update-key.ps1 -PrivateKeyPath "$env:USERPROFILE\mountain-fairytale-update.private.key"
```

Скрипт загружает официальный WinSparkle 0.9.2 с проверкой SHA256, создаёт ключ
Ed25519 за пределами репозитория и выводит только публичный ключ. Не запускайте
генерацию повторно для уже выпущенного приложения: установленные клиенты
доверяют первоначальному публичному ключу.

В Settings → Secrets and variables → Actions репозитория:

| Тип | Имя | Значение |
| --- | --- | --- |
| Secret | `UPDATE_PRIVATE_KEY` | Полное содержимое созданного файла закрытого ключа |
| Variable | `UPDATE_PUBLIC_KEY` | Только base64-строка после `Public key:` |
| Variable | `API_BASE_URL` | Начальный адрес локального API, сейчас `http://192.168.0.25:8000`; пользователь может изменить его в настройках |

Закрытый ключ хранить также в защищённой резервной копии. Он не попадает
в приложение, артефакты, Git или журналы workflow. GitHub-токена в приложении нет.
Публичный ключ не секретен. Без него developer/PR-сборка работает, но обновления
отключены; выпуск по тегу требует все три настройки.

## Подготовка и публикация

1. Изменить `version` в `pubspec.yaml`, например `1.1.0+1`, и `release-notes.md`.
   Часть до `+` — публичная SemVer-версия; CI заменяет часть после `+` своим
   возрастающим `github.run_number`. Каждый Windows-компонент ограничен 65535;
   workflow остановится при превышении, номер не обнуляется.
2. PR в `master`: анализ, все автономные unit/widget-тесты, тесты release-скриптов,
   Windows-сборка и установщик. Версия Flutter зафиксирована: 3.47.4.
   Анализ блокирует ошибки; старые warning/info пока видны, но не блокируют CI.
3. После merge создать и отправить тег, совпадающий с версией: `v1.1.0`.
   Commit тега должен принадлежать истории `master`.
4. Дождаться успешного **Flutter Windows CI** на теге. Артефакт
   `windows-release-v1.1.0` содержит Setup.exe, `appcast.xml`, `update.json`
   и `SHA256SUMS`. Установщик подписан Ed25519; пара ключей проверяется.
   Тег сам не публикует релиз и не уведомляет пользователей.
5. Actions → **Publish Flutter release** → Run workflow на `master` →
   `version_tag = v1.1.0`. Скрипт скачивает готовый артефакт успешной проверки
   именно этого тега, проверяет SHA256, подпись, версию и commit. Создаёт draft,
   загружает все файлы и только затем публикует его как latest.

Публичные версии не перезаписываются. Публикация должна увеличивать версию.
При ошибке загрузки остаётся draft: проверить причину, удалить незавершённый
draft вручную и повторить публикацию. Готовые Actions-артефакты хранятся 30 дней.
Если артефакт истёк, подготовить новый выпуск с новой версией.

## Поведение приложения

Адрес API меняется через шестерёнку «Настройки приложения», без новой сборки.
Сохранённое значение имеет приоритет над адресом из сборки и сохраняется при
обновлении. Подробности: [настройки сервера](server-settings.md).

- После первого кадра и раз в четыре часа проверяется небольшой `update.json`.
  Это пассивная проверка: значок получает отметку, никаких окон установки.
- По кнопке показываются текущая версия, новая версия и описание изменений.
  Пользователь может отложить обновление. Приложение продолжает работать.
- Запуск обновления доступен с основного экрана и экрана входа. Пока открыт
  редактор или модальная форма, обновление не запускается. После подтверждения
  блокируется редактирование до закрытия окна WinSparkle или выхода приложения.
- WinSparkle самостоятельно загружает установщик и проверяет Ed25519-подпись.
  При неверной подписи установка запрещена. Dart не заменяет работающий exe.
- После подтверждения в окне updater приложение закрывается без logout.
  Установщик ждёт завершения процесса, показывает прогресс, обновляет файлы
  и запускает новую версию. При первой ручной установке запуск предлагается.
  Он не принудительно завершает другие процессы.
- Нет интернета, нет первого релиза или сбой GitHub: проверка не мешает работе.
  Повторить её можно кнопкой. До первого опубликованного релиза ответ 404 нормален.

Нативный мост использует WinSparkle 0.9.2, а не старую DSA-версию, поставляемую
Flutter-плагином auto_updater. Callback-и передаются на главный поток Windows
через сообщения окна; на worker-потоке Flutter API не вызывается.

## Совместимость с ZIP и данными пользователя

Закрыть старую ZIP-версию, поставить Setup.exe и запускать новый ярлык.
Имя exe, CompanyName/ProductName в Runner.rc и реализация token/preferences
хранилищ сохранены: авторизация, тема и настройки окна остаются в прежнем
пользовательском профиле. Папка ZIP больше не используется для обновления.
Удаление программы не удаляет профиль и токены.

Установщик включает app-local Visual C++ runtime из Visual Studio; отдельная
установка VC++ Redistributable с UAC не нужна. WinSparkle DLL и лицензии также
включены. Подпись обновления не является Windows Authenticode: предупреждение
SmartScreen для первого установщика возможно.

## Приёмка перед первым публичным выпуском

Автоматически проверяются формат feed, сравнение версий, сбои сети,
пользовательское подтверждение/отмена, запрет обновления при открытом редакторе,
блокировка работы во время native updater, целостность артефакта и подпись.

На целевой Windows отдельно пройти реальный интерфейс двух тестовых сборок A/B:
установка без UAC → вход и изменение темы/размера окна → обновление по кнопке →
запуск B с теми же настройками и авторизацией. Проверить «Позже», отмену загрузки,
обрыв интернета и открытую несохранённую форму. Тестовые сборки и ключи не
публиковать как latest. До этой приёмки этап полностью закрытым не считать.

Для закрытой локальной приёмки debug-сборка поддерживает
`--dart-define=UPDATE_FEED_URL=http://127.0.0.1:8765/appcast.xml` и отдельный
временный `UPDATE_PUBLIC_KEY`. В Profile/Release HTTP-исключение отсутствует:
нативный мост принимает только штатный HTTPS appcast этого GitHub-репозитория.
Локальные установщики и feed лежат в игнорируемой `tmp/operations/acceptance/`;
они не являются артефактами для публикации. Тестовый сервер слушает loopback,
после ручной приёмки его нужно остановить. Рабочий приватный ключ для этой
проверки не используется.

Основной контракт: backend `docs/contracts/operations-deployment-updates.md`.
